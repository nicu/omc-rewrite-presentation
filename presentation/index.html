/ 01Words we will use

Five words, before we start

These come up on every slide. Nothing here is new to the business — only to the code.

  • BrandOne of the ~50 websites we runAtlas Rewards, Cabana Travel
  • VerticalA kind of thing you can bookstays, flights, cars, cruises
  • Business modelHow a brand lets you pay for itpoints, member rate, certificate, plain cash
  • LayoutA page shape with named gaps in ita filter rail, a toolbar, a list of results
  • SlotOne of those gaps, and whatever fills itthe filter rail is a slot; a brand can fill it differently

The whole idea in one line: a page is a layout with its slots filled in. Adding a brand or a vertical should mean filling the same slots differently — not building another page.

Step 1 — start with something that only takes props

A flight result card. It knows nothing about where the data came from or who is looking at it. 

export const FlightResultCard = ({ flight, businessModel }) => (

so far

Card, Text and PriceDisplay already existed — they came from the stays work. This file is 100 lines and it is the only new drawing code flights needed.

worth saying out loud

This card is not reusable across verticals, and it should not be. A flight row and a hotel row are different things. What we reuse is everything around it.

three gaps

filters, toolbar, results. Leave filters out and the left column disappears. That is how a cash-only brand, which has nothing to choose, gets a full-width page with no extra code.

reused as-is

Stays and flights both use this file. So do the two shared controls that go in filters and toolbar.

/ 05Let us build one

Step 4 — and what is that <Scope>?

It carries the region’s name down the tree, so events from far below can say where on the page they happened.

how it works today

export const FlightSearchRegion = ({ destination }) => {
  const { data, status, Scope } = useLoad(
    { results: flightSearchQuery(criteria) },
    { name: 'air.search' },
  );

  return (
    <Scope>          // below here is tagged air.search
      <SearchLayout … />
    </Scope>
  );
};

// so a card three levels down sends
PRODUCT_SELECTED  region=air.search

an alternative, if we prefer it

// the page says where each region sits
<Region name="air.search"><FlightSearchRegion /></Region>

// and the region has no wrapper to remember
export const FlightSearchRegion = () => {
  const { data, status } = useLoad({
    results: flightSearchQuery(criteria),
  });

  return <SearchLayout … />;
};
why it exists at all

React only passes this downwards, and useLoad runs inside the region — so it cannot reach above itself. It hands the wrapper back instead.

the honest cost

“Always remember to wrap your output” is a bad rule. Forget it and nothing breaks — events just quietly lose where they came from.

Step 5 — the card lists what can happen to it

It says what the events would carry. It does not say what they are called. 

type Actions = {
  impression: ProductListPayload;   // scrolled into view
  select:     ProductListPayload;   // clicked
  expand:     ProductPayload;       // opened fare conditions
};

export const FlightResultCard = ({ flight, businessModel, track }) => {

  const t = useTracking<Actions>(track, {
    impression: () => base,
    select:     () => base,
    expand:     () => base,
  });

  const ref = useOnVisible(t.impression);

  return ( /* … the card from step 1 … */ );
};
one prop

However many things the card can do, it takes one track prop. Not one callback per interaction threaded through the layout.

costs nothing unused

The data for an action is only built if someone asked for that action. A card with no tracking, in a list of 200, does no work at all.

why not put it in the card

The same card appears in places where a click means something different, or nothing at all. If the card picked the event name, you would need a second card for the second place.

it is checked

An event that does not accept product data cannot be used here. It is a build error, not something we find in the data three weeks later.

/ 05Let us build one

Step 6 — errors go to a toast, the same as today

export const FlightSearchRegion = ({ destination }) => {

  const { showFailure } = useToast();

  const { data, status, retry, Scope } = useLoad(
    { results: flightSearchQuery(criteria) },
    { name: 'air.search', onFailure: showFailure },
  );

  return ( /* … unchanged from step 4 … */ );
};

The API gives us a message, not an error code, so there is nothing to look up — we show what it said. Anything without a message falls back to a generic line from the errors translations.

logged either way

The failure is reported to analytics whether or not it is shown, tagged with the page it came from. Nothing to remember at the call site.

the page chooses

A toast for anything the user can retry. An empty state in the results list. A full-page panel only when there is genuinely nothing to render.

/ 06Now change something

Adding a brand

A brand is a folder with two files in it. Nothing in it is required.

src/brands/cabana/brand.tsx

import { SelectChoice } from '@/components/atoms';
import { FooterNote } from './slots';

export const cabana: BrandConfig = {
  id: 'cabana',
  name: 'Cabana Travel',
  analytics: { partner: 'CABANA', brandKey: 'CBN' },

  theme,   // the MUI theme — where nearly all the look lives

  businessModels: ['cash'],       // cash only — no points, no tiers
  defaultBusinessModel: 'cash',
  accountSections: [ … ],

  // Optional. Delete it and every page still works.
  overrides: {
    PaymentChoice: SelectChoice,
    FooterNote,
  },
};
a component, not a keyword

SelectChoice is a real component. Ctrl-click it and you see exactly what it draws. Compare that with writing shape: 'select', where you have to go and find out what 'select' means.

everything is optional

Cabana lists no promo strip and no sign-in message, so neither appears — nothing to switch off. And there is no showBalances: false: we work out that Cabana has no loyalty programme because businessModels is cash only.

the theme does the work

theme.ts next door is 20 lines: colours, corner radius, spacing, fonts, and whether cards have a shadow. Everything you can see on the page comes from there, not from components.

/ 08To decide together

Open questions

None of these have an answer in the prototype. They are the reason for the meeting.

01

How do we fill the gaps in a layout?

Pass each piece as a prop, or nest them as children. Both are written — SearchLayout.tsx and SearchLayoutCompound.tsx — and render the same markup. Props are harder to get wrong; children reorder more freely.

02

Should the two search pages share more?

They are 95 and 94 lines and differ in 31. That could be a shared SearchRegion, or it could be the right amount of duplication.

03

Do we keep the data component pattern?

It cannot go in Storybook, and it hands back a Scope you have to wrap your output in. I could not remove that line.

04

Is a business model the right unit?

The prototype treats it as a first-class thing brands offer per vertical, which matches what the API returns. It may not survive contact with the odder brands.

05

Where does this get built first?

One page, on top of what exists, with the old components still inside it — or one complete vertical.
