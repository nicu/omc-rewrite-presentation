export const AppHeader = ({ nav = [], actions }) => {
  const brand = useBrand();
  const MembershipBanner = brand.overrides?.chrome?.MembershipBanner;
  const brandActions    = brand.overrides?.chrome?.headerActions ?? [];
  const [menuOpen, setMenuOpen] = useState(false);

  return (
    <header>
      {MembershipBanner && <MembershipBanner />}   // a gap
      <Logo />

      // the row, when there is room for it
      <nav>{nav.map(item => <NavLink … >{item.label}</NavLink>)}</nav>

      <Stack>
        {brandActions.map(…)}                // a gap that is a list
        {actions}
        <button onClick={() => setMenuOpen(true)} />
      </Stack>

      // the same list again, when there is not
      <Modal open={menuOpen} …>
        <nav>{nav.map(item => <button …>{item.label}</button>)}</nav>
      </Modal>
    </header>
  );
};
the nav is a list

Because it is data rather than markup, the header can draw it twice: as a row of links across the top, and as a menu behind a button. Same four destinations, two shapes, one source.

a fixed run of markup cannot do that

Four <NavLink> children written out by hand can only be shown or hidden. There is nothing to re-draw as a menu, because there is no list — only a block of JSX the header cannot look inside.

a gap can fetch

A brand may put a points balance in headerActions, and that component loads the balance itself. The header does not know anything inside it talks to a server.

src/telemetry/context.tsx · where the name is attached

export const useEmit = () => {
  const context = useContext(AmbientCtx);  // brand, vertical, region…
  const adapters = useContext(AdaptersCtx);

  return (event, properties) => {
    const payload = { event, properties, context };
    for (const adapter of adapters) adapter.send(payload);
  };
};

// a card three levels down passes the product and nothing else
emit('PRODUCT_SELECTED', { productId, productName, position, listId });
why it is a wrapper

React context only travels downwards. The name has to be set above the region, so the region’s own useLoad can read it too.

why it is outside

Put it inside and the region has to say its own name twice: once for the wrapper, once for useLoad. From outside, the string is written once, in the one file that knows what page this is.

what it carries

The region name, the vertical, and how the reader is paying. Brand and partner are already set once at the root. Nothing below ever builds a name itself.

/ 05What a change costs

Adding motion — four questions, four owners

Animation is the first thing that tempts everyone into writing a brand-specific component. It does not have to be, as long as these four questions stay separate.

The questionAnswered inApplies to
Does this brand move at all? theme.animates A yes or no. Leave it out and the brand does not move — and no wrapper renders at all
How far, how fast, how far apart? design tokens The scale everything picks from. A brand retunes it in its brand stylesheet, beside --space-unit
Which way, and which step of each? the call site That section, in every brand. A login page can rise slowly and a deals grid slide in one card at a time
Is this section a different thing entirely? overrides That section, in that brand — a carousel instead of a grid

Fold motion into the third row — AnimatedFeaturedDestinations — and the other two multiply into it. Next comes CarouselFeaturedDestinations, then AnimatedCarouselFeaturedDestinations, each one re-implementing the section body. That is how eight headers happen. Kept apart, a new component is needed only when the thing changes, never when the motion does.

Take the payment

The one thing here that cannot be undone, and the only one that has to survive being interrupted. The reader leaves the site mid-call and comes back on a URL.

src/regions/checkout/PaymentStep.tsx

// The button calls this with no token. The return from the bank calls
// the same function with one. That is the only difference between them.
const authorise = async (cartId: string, authToken?: string) => {
  try {
    const result = await api.authorise(cartId, authToken);
    if (result.status === 'challenge') {
      // Not an error. Hand over to the issuer and stop here.
      emit('PAYMENT_CHALLENGED', { step: 'payment' });
      setChallenge(result.challengeId);
      return;
    }
    emit('CHECKOUT_COMPLETED', { step: 'payment' });
    clearDraft(cartId);
    onDone();
  } catch (error) {
    // Drop a token the bank rejected, so a refresh cannot try it again.
    if (authToken) router.replace({ name: 'checkout', step: 'payment' });
    showFailure(error);
  }
};

…and the second entry point into it

why it is interruptible at all

A challenge is a normal answer, so it comes back in the return value instead of being thrown. The call stops, the issuer takes over, and the page is left behind. Nothing is held in memory waiting, because nothing survives the reader leaving.

so there is nothing to resume

The step is an address and the answers are on the cart. Coming back means loading the cart and calling authorise again with the token from the URL. The token is the only thing carried across, and it is not private.

what actually prevents a second charge

The server. A cart it has already taken payment on gets the same authorisation back rather than a new one, so a double-tap, a refresh, or arriving twice from the bank still leaves one charge. That guarantee is the server’s, not ours.
